# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Nubo is an Android-only weather app, written in Kotlin with Jetpack Compose. Forecast data (current/hourly/daily) comes from Open-Meteo and works **worldwide**; location search comes from Open-Meteo's geocoding API, reverse geocoding (the "my location" button) from BigDataCloud. Weather warnings (avisos) are **Spain-only**, from AEMET's CAP/XML endpoint. State is a single `WeatherViewModel` exposing a `StateFlow`; persistence is DataStore Preferences.

The app was migrated from Flutter; v1.0.0 was the first native Kotlin release, succeeding v0.1.36. `main` is the Kotlin code and the only deployable branch.

## Commands

```bash
./gradlew testDebugUnitTest        # unit tests
./gradlew assembleDebug            # debug APK
./gradlew assembleRelease          # release APK (signed if key.properties exists)
./gradlew lintDebug                # Android lint
./gradlew :app:testDebugUnitTest --tests "*DailyCodeAggregatorTest*"   # single test class
```

Test results are XML under `app/build/test-results/`; the Gradle console output does not list individual tests.

Requires JDK 17+ (`local.properties` must point `sdk.dir` at the Android SDK).

### Release / deploy

`deploy.sh` does not bump anything — it reads `versionName` from `app/build.gradle.kts`, runs the tests, commits, tags `vX.Y.Z` and pushes the tag. That triggers `.github/workflows/release.yml`, which builds, signs with the keystore from the `SIGNING_KEY` secret, verifies the signature and publishes a GitHub Release, keeping only the latest 3.

So: bump `versionName` **and `versionCode`** in `app/build.gradle.kts` first, then run `./deploy.sh`. The script aborts if the tag already exists.

**`versionCode` must increase on every release.** The Flutter app shipped every version with `versionCode = 1` because `pubspec.yaml` never had a build number; Android needs it to go up to accept an update.

**Always test on an emulator/device before deploying.**

## Architecture

Layered under `app/src/main/java/com/nubo/nubo/`:

`data/remote` + `data/local` + `data/location` (raw HTTP, DataStore, GPS) → `data/repository` (interfaces + one `Impl`) → `ui/weather/WeatherViewModel` → `ui/weather` screens + `ui/components`.

Pure logic lives in `domain/` and has no Android dependencies, which is what makes it unit-testable without instrumentation.

Dependencies are resolved by hand in `di/ServiceLocator.kt` — no Hilt. One ViewModel and a handful of services do not justify an annotation processor.

Key components:
- `data/remote/OpenMeteoApi.kt` — one call returns hourly + daily. The request asks for the full seven days; the **hourly list is capped at `HourlyForecast.MAX_HOURS` (24)** when parsed, because past the day the hour-by-hour detail says nothing the daily summary does not. `DailyForecast` keeps all seven days: it aggregates the raw `hourly` block of the JSON itself, not that capped list, so trimming does not weaken the daily icons. `apparent_temperature` and `uv_index` ride along in this same request — they feed the conditions card at no network cost. Returns the **raw JSON**, which is what gets cached, so the cache does not break when model shapes change.
- `data/remote/AirQualityApi.kt` — European AQI from Open-Meteo's **separate** air-quality endpoint, so it is a second request per location. It is fired in parallel with the forecast inside `WeatherRepositoryImpl` (chaining them would double every refresh for a secondary figure) and its failure is swallowed: the forecast still lands and the tile shows a dash, the same contract as alerts outside Spain. Only two days of hourly index are asked for — about 1 KB.
- `data/remote/AemetApi.kt` — AEMET's two-step protocol: the endpoint returns a signed URL in `datos`, and the payload is fetched from there.
- `data/remote/AlertService.kt` — CAP parsing. AEMET concatenates several `<alert>` blocks in one body, so they are split with a regex before parsing. The regex uses a negative lookahead so a truncated block does not swallow the next valid one. Alerts are matched **by the full 6-digit warning zone**, not by a province prefix — see below.
- `data/remote/GeocodingApi.kt` — Open-Meteo geocoding, free and keyless. The source of every new location: name, country, region, coordinates and IANA time zone. Ids are prefixed `om:` so they can never be confused with a legacy INE code.
- `data/remote/ReverseGeocodingApi.kt` — BigDataCloud, for the "my location" button. Open-Meteo geocodes forward only. Ids are `geo:lat,lon` rounded to 4 decimals so tapping twice does not create duplicates.
- `data/remote/AemetZoneService.kt` — downloads AEMET's ~8.000-municipality master once and keeps it in memory. Since search moved to Open-Meteo it only does two Spain-only jobs: resolve the **warning zone** (`zona_comarcal`) of a point, and fill in coordinates for cities saved in the old INE-only format. The download is lazy: someone who never looks at a Spanish city never pays for it.
- `data/local/WeatherStorage.kt` — DataStore. Stores the raw Open-Meteo JSON plus alerts and sun times per location.
- `data/local/FlutterPreferencesMigration.kt` — **do not delete while Flutter users remain.** Reads the SharedPreferences the Flutter app left behind (same package) so updating does not wipe saved cities. The value format is `<base64 prefix>!<json>`; the `!` is undocumented and was found by dumping the real file.
- `domain/astro/SunCalc.kt` — own port of the SunCalc algorithms, replacing the Dart packages. Validated against physical facts (solstice day lengths, polar night, synodic month) rather than copied values.
- `domain/weather/DailyCodeAggregator.kt` — recomputes the daily icon from the hourly codes. Open-Meteo's `daily.weather_code` is the *most significant* phenomenon of the day, not the most durable, which made the icon systematically pessimistic.
- `ui/components/HourlyView.kt` — hourly carousel plus the temperature chart. Its `SectionTitle` sits **outside** the card, aligned with the one over the daily rows: those two are the only uses of that component and both are section headings for a stretch of the page, so having one inside a card and the other above a list made them read as different things. The Sol/Luna labels stay inside their tiles, but they are not headings — they label a tile, and do not use `SectionTitle` at all. The column width is **computed** from the card width so exactly `VISIBLE_HOURS` (6) fit; it used to be a fixed 65 dp, unrelated to the screen, which cut the sixth hour in half. Scrolling snaps in blocks of six through `blockTarget`, which clamps the fling's projected landing to the two adjacent blocks so one gesture always moves one block. Three things about that gesture are load-bearing and were each a bug once:

  - The column width comes from `columnWidthPx`, which **truncates to whole pixels**, and the block is six of those. Computing the block separately in `Dp` made it 1160 px while six measured columns were 1158 — two pixels per block that accumulated into a visibly misaligned carousel after a few swipes.
  - The scroll viewport is one block wide, **not** the card width, so the total travel is an exact whole number of blocks and the last one can be reached.
  - `performFling` returns early when it is already on target. Handing the finger's velocity to a spring with nowhere to go made it overshoot past the boundary; `scrollBy` swallowed the impossible part but not the way back, so swiping against the start of the list pushed the carousel most of a column inwards.

  The gesture lives on the whole card, not just the hour row: the chart sits outside the scrollable area, so the row uses `horizontalScroll(enabled = false)` purely for its offset while the enclosing column owns the gesture. `stayInsideCard` eats the leftover horizontal scroll and fling so reaching either end never leaks into the city pager — the two swipes are the same finger movement and used to collide exactly where nothing should happen. That leftover is also what feeds `EdgeResistance`, which pushes the card a little and springs it back: Android's own overscroll cannot be used here, and not for lack of trying. The leftover is dispatched to the parents — where `stayInsideCard` has to take it so the city does not change — **before** the overscroll effect ever sees it, so letting it through for the effect to work is precisely handing the gesture back to the city pager. `edgePull` damps the push with a hyperbolic tangent, so it never reaches its limit no matter how hard you pull. The chart is **not** inside the scrolling area: it spans the whole card and draws itself offset by `scrollState.value`, which keeps the curve in step with the columns without re-measuring 48 of them. Its min/max are computed over every hour, so the vertical scale does not jump between blocks. There is deliberately no y-axis legend: every point already carries its own temperature label, and the axis bounds were the padded limits of the chart, not values any hour actually reaches. Both curves are drawn through `extendToEdges`, which adds one extrapolated point at each end so they reach the card border instead of starting in mid-air half a column in — those points get no dot and no label because they are not hours. The hour list is trimmed to a multiple of six so the last block cannot land half-way, showing a clipped column at each edge; `HourlyForecast.MAX_HOURS` is already a multiple of six, so this only bites on a short payload.
- `ui/weather/WeatherScreen.kt` — the header collapses as the page scrolls: **one** city name travels from its place on the page to the top bar, next to the hamburger, shrinking on the way. It used to be two Texts crossfading, one dying where the other was born; it read as a relay, not as a name that moves. The travelling name is drawn **above everything**, not inside the page, because the page's scroll container clips at its top edge and a name climbing past it would simply stop being drawn — so the page keeps an invisible copy that only holds the space and **measures** where the journey starts. Both ends are measured rather than computed: the start moves with the scroll and the end depends on how much the menu takes. The measurement is stored **with the id of the city that took it**: a page that is loading or failed draws no big name and therefore measures nothing, and without the id the stale position of the previous city would be used — printing the name twice, once travelling and once inside "Cargando…". `unclippedBounds()` exists for the same reason the overlay does: `boundsInWindow()` returns what is actually visible, which goes empty exactly when the name leaves the viewport. Only the page being viewed hands its name over; the neighbours draw their own, which is what you see slide in when changing city. A location pin fades in beside the name over the last quarter of the travel — earlier it would read as a loose icon in the middle of the screen rather than the mark of where the name has landed. It holds its place in the row from the start even while invisible: appearing by making room would shove the name aside exactly as it settles. **The pagination dots fade out over the first half of the travel**, long before the name rises into the bar's band — the dot row is centred and grows with every saved city, so with a handful of them the name would cross it. The guarantee is no longer that the two are never visible at once (the name now always is) but that while the dots are still there the name is still below them, and a test sweeps the range to keep the dots gone before the halfway point. Sliding between cities interpolates the gradient over the pager's **absolute position** (`currentPage + currentPageOffsetFraction`): the two jump together at mid-gesture, so only chained do they give a continuous value. The animations cannot be mixed the way a gradient can — there is no half rain, no half star — so `sceneAlpha` fades them to zero exactly at the midpoint, swaps them there unseen, and brings them back; when both pages share an animation nothing fades at all. Each page keeps its own `ScrollState` in a map hoisted above the pager, because the bar needs the scroll of the page being viewed; they are built by hand since the page count varies and `remember` cannot be called a variable number of times. **Leaving a city returns it to its starting state** — scrolled to the top, hourly carousel back on "Ahora", no day unfolded — by bumping that page's entry in `pageGenerations`, which is a `key()` around the page and therefore throws away every `remember` inside it. Resetting by discarding the composition rather than hoisting and clearing each piece keeps working for whatever is added to a page later. It happens on `settledPage`, when the page being left is already off-screen, so the rebuild is never seen; the vertical scroll is reset separately because it lives outside the key.
- `ui/components/DailyView.kt` — one row per day, and each row **unfolds** to show that day's conditions: worst air quality, maximum UV, mean humidity and the apparent-temperature range. They are figures for the **whole day**, today included: the same card shape must not mean two different things depending on which row you opened. Only one row can be open, and that is guaranteed by storing a single date (`toggledExpansion`) rather than closing the others in turn, where forgetting one would be enough. The chevron points **right when closed and down when open**, following the content: closed it points at where the detail is tucked away, open it points at what has just appeared below. The down/up pair would have the open state pointing away from what it revealed, and seven identical down arrows in a list read more like "keep scrolling" than "this opens". UV, apparent temperature and humidity are daily fields of the forecast call that was already being made, so they cost nothing and cover all seven days; air quality has no daily block of its own and is aggregated from its hourly series in `CityWeather.airQualityByDay`. CAMS runs out around the fifth day, so the last rows show a dash there — the tile stays put so the grid does not change shape depending on how far the model reaches.
- `ui/components/GlassCard.kt` — translucent card with a scrim that occludes the rain falling behind it. Compose has no native backdrop blur.
- `ui/components/WeatherEffects.kt` — rain, snow and lightning on a Canvas, following Breezy Weather's approach. Snowflakes are drawn as swaying dots, not streaks: falling straight they read as slow rain. Lightning is deliberately restrained — one flash every 9-20 s at a peak veil of `MAX_FLASH_ALPHA`. It used to be every 3-8 s at twice the opacity, which reads well but flickers the screen often enough to tire anyone, and to genuinely bother people sensitive to flashing. Both limits are pinned by tests.
- `ui/components/NuboWeatherIcons.kt` — hand-drawn cloud-with-precipitation icons, reusing the cloud from `Icons.Outlined.Thunderstorm`. Material has no equivalent.
- `ui/weather/LocationList.kt` — the drawer's saved-location cards. Swipe right deletes (armed past 40% of the width, with haptics and a red backdrop); long-press picks a card up to reorder. The two gestures coexist because the reorder one needs a long press and **consumes** its events, which cancels the horizontal detector's own slop; without that consumption a diagonal drag fires both. Cards are painted with opaque colours (`CARD_IDLE`/`CARD_SELECTED`, the drawer background already blended with white) — translucent ones let the delete backdrop and its label show through the city name. The reorder arithmetic (`reorderTarget`/`reorderShift`) is pure and unit-tested; it assumes every card is the same height, so it divides by the pitch instead of measuring.
- `ui/weather/SettingsPanel.kt` — background interval, update check and about. They live **inside the drawer**, in place of the location list, not in a layer above it: the gear turns into a back arrow and the two contents cross-fade in the same box, so the menu never has anything on top of it and is always left the way it was entered. `MainActivity` owns the flag so it can reset to the list when the drawer closes and let the system back button return to it. There is no "refresh now": pull-to-refresh on the main screen does the same thing. `UpdateService.checkForUpdates` reports three outcomes, not two — a release newer than this one, nothing new, or the check itself failed. It used to return `null` for the last two together, which forced the button to stay silent: saying "you are up to date" with no network would be a lie. The **manual** check confirms both quiet outcomes in a dialog; the one at startup still only ever speaks when there is something to install.
- Adding a location is the drawer's floating action button, bottom-right, where Material puts a screen's primary action; it used to be one more card at the end of the list, which fell out of view once there were a few cities. The list reserves bottom padding for it, and it lifts out of the way while the delete snackbar — which spans the drawer's width — is showing.

- `work/BackgroundUpdateWorker.kt` — WorkManager periodic refresh; builds its own dependencies since it runs without UI. It is also the only place a new warning is ever discovered, so turning alert notifications on schedules it every `ALERTS_ONLY_HOURS` even with background updates set to Off — and the settings screen says so under the switch rather than overriding a preference quietly.
- `domain/weather/AlertNotifications.kt` + `data/notification/AlertNotifier.kt` — notifications for new AEMET warnings, off by default. AEMET publishes no stable id across downloads, so an alert's identity is composed of where, what, which level and **for when**: including the expiry is what makes an extended warning count as new while re-downloading the same one does not. Keys of already-announced alerts live in DataStore and are pruned to those still active, and they are only written when the notification really could be posted — recording one the system dropped would silence it forever. Expiry is judged in the **location's** zone, like everything else that compares a timestamp. The switch does not turn on until Android grants `POST_NOTIFICATIONS`; once permanently denied the system stops asking and returns a silent "no", which is why there is a dialog pointing at the system settings.

### Time zones

Open-Meteo returns timestamps already in the location's time zone (`timezone=auto`), so they are parsed as `LocalDateTime`. Until v1.1.0 they were then compared against the **device** clock, which only works while the device and the location share a zone. That made "Ahora", "Hoy", the sun arc and alert expiry wrong for any foreign city — and it was already subtly wrong inside Spain, where the Canaries run an hour behind the mainland.

Every one of those comparisons now uses the **location's** zone:

- `CityWeather.sunPhase` is **per city**, computed with that city's clock through `sunPhaseAt`. There is no application-wide sun phase and there must not be one: when there was, sliding from A Coruña to Toronto painted Toronto with the midday blue and Toronto's stars on top of it — the gradient came from the global phase while the stars came from the location's own hourly code.

- `SavedLocation.timeZone` / `CityWeather.timeZone` carry it, and `CityWeather.nowThere` is what the UI compares against. `zoneOf()` in `domain/model/Zones.kt` falls back to the device zone rather than throwing.
- The authoritative value is the `timezone` field of the forecast response, not the one from geocoding: it is the zone the timestamps in *that* payload are expressed in. It is written back to the saved location on every fetch.
- `SunCalculator` and `MoonCalculator` take a `ZoneId` that **defaults to the device zone**. Forgetting to pass it is silent and wrong — it put Tokyo's sunrise at 22:08.
- CAP alert times get the zone too, so a Spanish warning reads correctly from abroad.

Adding a new place that compares a forecast timestamp to `LocalDateTime.now()` reintroduces the bug.

`java.time` works on `minSdk 24` thanks to core library desugaring, enabled in `app/build.gradle.kts`.

### AEMET warning zones

AEMET issues warnings per **zone**, which is sub-provincial: A Coruña has four, and three of them are coastal. The zone is the 6-digit `geocode` in each CAP alert — area (2) + INE province (2) + zone (2).

The zone of a municipality is the `zona_comarcal` field of AEMET's municipality master, and it matches that geocode exactly. All 8.122 municipalities carry it, so there is no fallback path to maintain.

Until v1.0.0 the filter compared only the first 4 digits, so every municipality got the warnings of its whole province — an inland town showed coastal warnings. Matching the full zone is what fixes it, and it must stay an **equality** check: a prefix comparison is what caused the bug.

The first 2 digits of the zone are the AEMET area the endpoint is queried by, so no province → area table is needed. The hand-built one that used to live in `AemetApi.kt` was verified to agree with `zona_comarcal[:2]` for all 8.122 municipalities and then deleted. Note it never worked in the Canary and Balearic Islands anyway: there AEMET does not use INE province digits in the zone code (Adeje is `659603`).

## Gotchas

- The AEMET API key is baked into `AemetApi.kt`, as it was in the Flutter app. It is a free public OpenData key already published in previous APKs and in the git history.
- The air-quality series is stored and re-read like the forecast, **as an hourly series and not as a single "current" value**: the cache keeps the raw JSON, so hours later the current hour has to be picked again. One stored "now" value would be served stale while the temperature beside it stayed correct.
- **Warnings exist only in Spain**, and so are their notifications. `AlertRepositoryImpl` returns an empty list everywhere else. The candidates for widening it are MeteoAlarm (≈38 European countries, but its CAP carries only an `EMMA_ID` with no polygon, so it needs the zone geometry from somewhere) and the US NWS (`api.weather.gov`, free, keyless, and it resolves the zone server-side from `?point=lat,lon`).
- **Saved locations have two id formats.** New ones are `om:` or `geo:` prefixed; anything without a colon is a legacy INE code from a version before the app went worldwide, is assumed to be in Spain, and gets its coordinates filled in from AEMET's master on first launch (`WeatherViewModel.completeLegacy`). Do not delete that path while those installs remain — same reasoning as `FlutterPreferencesMigration`.
- **Precipitation icons carry the intensity**: 61/63/65 and 80/81/82 are three different drawings, and so are 71/73/75. They used to share one, so "Lluvia débil" and "Lluvia fuerte" were only ever told apart by the text in the city header — while the daily rows and the hourly carousel show the icon alone. The ladder does not lean on counting strokes: light is two **long** strokes (drizzle is two short ones), moderate three, heavy four longer and thicker. At 24 dp three versus four strokes is not a difference anyone reads, so the step carries number, length and weight at once.
- Weather icons are mostly Material approximations: `material-icons-extended` has no "sun behind cloud" or `Foggy` equivalent to Lucide's. Precipitation is the exception — those are drawn in `NuboWeatherIcons.kt`.
- **The UI is translated.** `values/` is English — it is the fallback for every locale without its own folder, so it is the base — and `values-es/` is Spanish, the language the app was written in. `res/xml/locales_config.xml` declares both so Android offers the per-app language picker.
- Date formatters take **no explicit locale**, and that is deliberate. They used to pin `es-ES`, correctly, because otherwise day names came out in the device's language inside a UI that only spoke Spanish. The moment the UI became translatable that fix turned into the bug — it would put "lunes" inside an English screen — so `Locale.getDefault()` is now the right answer everywhere.
- **The domain layer must never hold display text.** It has no Android dependency, which is what makes it unit-testable without instrumentation, so it cannot reach resources. Sky conditions, moon phases, air-quality bands, UV bands, alert levels and alert families are all enums; `ui/components/WeatherLabels.kt` maps each to a `@StringRes`, the same split `WeatherIcons.kt` already used for icons. Errors follow the same rule: the data layer throws an `ErrorReason`, never a sentence, and `CityError.describe()` turns it into words.
- **AEMET publishes in Spanish and always will.** `AlertType.of()` matches its Spanish event text — that matching must stay Spanish because it is what the source emits — but what the app shows is the translated family name, not AEMET's string. The alert's own description text stays as AEMET wrote it.
- The language asked of the geocoding APIs comes from `apiLanguage()`, capped at the languages the app declares. It is not `Locale.getDefault()` verbatim because the admin-name trimming in `GeocodingApi` is hand-written for Spanish and English forms only; asking for a language nobody has pruned would show the long official names in full.
- **The order of the saved locations is the order of the pages**, and DataStore stores them in a `Set`, which has none. `WeatherStorage.saveLocations` writes the index as a prefix (`"0:…"`) and `loadLocations` sorts by it. Anything that reorders must go through those two.
- Robolectric is needed for tests touching `org.json`, pinned to `@Config(sdk = [34])` since it does not simulate API 36 yet.
